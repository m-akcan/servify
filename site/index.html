02 — Scale

One service. As many copies as you want.

Turn the replica count up and Servify starts more containers and balances traffic across the healthy ones. Try it on the right.

  • Four balancing strategiesRound-robin, least connections, sticky by client IP, or random. Plus WebSockets and TCP for databases.
  • Zero-downtime deploysNew replicas start next to the old ones and must pass health checks before traffic moves. A failed deploy never touches what's running.
  • Self-healingCrashed or deleted replicas come back on their own, with backoff for crash loops.
  • AutoscalingScale on requests per second or CPU, and back down gradually when it's quiet.

04 — Ready for real traffic

The boring parts, done properly. So you don’t have to.

Everything you’d otherwise bolt on with five more tools: certificates, alerts, backups, previews.

Automatic HTTPS

Add a domain and Servify gets a Let’s Encrypt certificate, renews it and redirects HTTP. Local apps get HTTPS too, from a private CA.

shop.example.comHTTPS · renews in 60d

Deploy on push

Signed GitHub, GitLab and Gitea webhooks deploy the second you push. In a monorepo, only the services whose folders changed. Deploy hooks for CI.

git push→building a1b2c3d

Alerts where you look

Slack, Discord, Telegram, ntfy, email or a webhook when a deploy fails, a service goes down, a backup breaks or a server runs low on disk or memory.

+ Slack · email · ntfy

Backups that restore

Scheduled dumps of Postgres, MySQL and MongoDB, archives for every other volume — to disk or any S3 bucket. One-click restore, with a safety backup first.

Environments & PR previews

Copy a project into staging with its own URLs and data. Every pull request gets a preview environment that disappears when it’s merged.

Paste a docker-compose.yml: services, variables, volumes and replicas carry over, and they still reach each other by name.

05 — Everything else

All the tools to run services. None of the ceremony.

Live logs

Stream and search logs across every replica, or download them.

Console

Run migrations and one-off commands inside any running replica.

Metrics

Requests per second, p95 latency, errors, CPU and memory per service.

Variable references

Point one service at another and it stays in sync. Drag between nodes to wire it up.

${{ postgres.DATABASE_URL }}

One-click rollback

Go back to any previous deploy, with a diff of what changed in its config.

Cron jobs

Give a service a schedule and it runs on time, with history, exit codes and output.

0 9 * * 1-5 → Weekdays at 09:00

Volumes and backups

Persistent volumes for your databases. Download any volume as a tarball.

Projects as code

Export a whole project to one file and import it anywhere.

servify.json

Built-in load tester

Send real traffic through the balancer and watch replicas and autoscaling react.

Database browser

Browse tables and rows in Postgres and MySQL, and run SQL that stays read-only until you allow writes. Nothing extra to install or expose.

Pre-deploy commands

Run migrations in a one-off container before the new version starts. If they fail, the old version keeps serving.

npm run migrate

Shared variables

Set a value once per project or environment and use it in every service. Secrets stay masked.

${{ shared.STRIPE_KEY }}

Image updates

See when a newer image or version is out and update in one click, or automatically. Moving a database to a new version takes a backup first.

App sleeping

Idle web apps stop after a while and wake on the next request, in about a second. Open connections keep them awake.

Several servers, one network

Add a machine with one command and place services on it. They still reach each other by name, with no ports opened between servers.

Local-first, no account

Servify runs on your computer, keeps its data in a SQLite file in your home folder and listens only on 127.0.0.1 by default. There's no sign-up and no telemetry.

Locked down by default

An owner password protects the dashboard, API tokens are stored hashed, and requests from other sites are rejected.

07 — Quick start

Running in a few minutes.

Clone, install, build, start. Then open the dashboard and hit Try the demo for a ready-made stack.

Node.js 22.18 or newer, and pnpm
Docker running locally
Nothing else: no database, no cloud account
$ git clone https://github.com/m-akcan/servify
$ cd servify
$ pnpm install
$ pnpm build
$ pnpm start
Open http://localhost:7700. Your apps are served at http://<service>.<project>.localhost:8080.
$ git clone https://github.com/m-akcan/servify
$ cd servify
$ docker compose up -d --build
Servify runs as a container and starts your services next to it. Ports are published on 127.0.0.1 only.
# create a token (or use the Agents page)
$ pnpm token my-agent

# add Servify to Claude Code
$ claude mcp add --transport http servify \
    http://localhost:7700/mcp \
    --header "Authorization: Bearer svf_…"
Any MCP client works. For stdio clients, the Agents page in the dashboard gives you the exact servify mcp command for your install.
# from a Servify checkout, on any machine that can reach it
$ npm i -g ./server
$ servify login http://your-server:7700

# upload, build and deploy the folder you're in
$ cd my-app
$ servify up --project shop --service web
$ servify logs -f
up follows your .gitignore. There's also deploy, run (a local command with the service's variables), exec, status and open.
Questions

Good to know

Do I need an internet connection?
Only to pull images or clone repos you don't already have. The dashboard, API and everything Servify itself needs runs offline.
Can I use it to host public websites?
Yes. Point your domain at the machine, let ports 80 and 443 reach Servify, and turn on automatic HTTPS: certificates come from Let’s Encrypt and renew on their own. Servify itself stays private by default — it only listens on your machine until you say otherwise.
Which AI agents work with it?
Any MCP client: Claude Code, Claude Desktop, Cursor and others. It supports Streamable HTTP at /mcp and a stdio bridge for clients that launch a command.
What happens to my services if Servify stops?
Your containers keep running in Docker, but the :8080 router stops with Servify, so their .localhost addresses go quiet. When Servify starts again it re-adopts everything and picks up where it left off.
Can I run services on more than one machine?
Yes. Servers → Add server gives you one command for the other machine; it only needs Docker, and it connects out to Servify, so it needs no open ports. Services on different servers still reach each other by name. That traffic goes through your main Servify machine, so keep an app and its database on the same server.
Is the canvas built on a diagram library?
No. The canvas and its spring-based animations are written from scratch, so dragging, zooming and live traffic stay smooth.
